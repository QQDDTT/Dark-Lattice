この設計ドキュメントは、AppMatrix プラットフォーム下の **モバイルファイルエディター (MobileFileEditor)** プロジェクトに関するものです。リリースおよびプロジェクト管理レベルでは、本プラットフォームは独立した **Android アプリ (MobileFileEditor_Android)** と **iOS アプリ (MobileFileEditor_iOS)** を同時に開発・リリースする必要がありますが、これらは同じ画面デザインと基礎的なビジネスロジックを共有しています。

この設計は React Native (Expo) に基づいて構築されており、両プラットフォームで完全に一致した精巧なすりガラスのカード管理とスムーズな編集体験を提供すると同時に、それぞれのネイティブプラットフォーム上で特有のコンポーネントやジェスチャーインタラクションに対して深い差異化適応を行うことを目的としています。

## 1. 両プラットフォーム独立プロジェクトアーキテクチャ

同じ画面デザインとユーティリティコードを共有しますが、`apps/` ディレクトリ配下で 2 つの独立したリリースプロジェクトに分割されています。

```text
apps/
├── MobileFileEditor_iOS/       # 独立した iOS プラットフォームリリースプロジェクト
│   ├── app/                    # ルーティングおよびページレンダリング層 (共有ページロジック)
│   └── src/                    # プラットフォーム特有のカプセル化 (例: iOS 専用 Action Sheet)
└── MobileFileEditor_Android/   # 独立した Android プラットフォームリリースプロジェクト
    ├── app/                    # ルーティングおよびページレンダリング層 (共有ページロジック)
    └── src/                    # プラットフォーム特有のカプセル化 (例: Android 物理戻るボタンの傍受)
```

## 2. ファイルシステムとローカルストレージの設計

両プラットフォームのアプリは Scoped Storage（パーティションストレージ/サンドボックスストレージ）を採用しており、それぞれがプライベートディレクトリ下のテキストを操作することで、危険な外部ストレージの読み書き権限の申請を免れています。

### 2.1 両プラットフォームのサンドボックスパスの違い
*   **iOS プラットフォーム**：`FileSystem.documentDirectory` に保存され、実際のパスは `/var/mobile/Containers/Data/Application/<UUID>/Documents/` となります。このデータは、デバイスのアップグレードや交換時に iCloud によって自動的にバックアップされます。
*   **Android プラットフォーム**：`FileSystem.documentDirectory` に保存され、実際のパスは `/data/user/0/com.appmatrix.mobilefileeditor.android/files/` となります。これは Android 内部の Scoped Storage に属しており、アプリがアンインストールされるとこのデータも一緒にクリアされます。

### 2.2 両プラットフォーム共有ファイルシステムインターフェースラッパー (`src/utils/fileSystem.ts`)
```typescript
import * as FileSystem from 'expo-file-system';

export const getBaseDir = (): string => FileSystem.documentDirectory;
export const SUPPORTED_EXTENSIONS = ['.txt', '.md', '.json', '.css', '.html'];
export const MAX_FILE_SIZE = 2 * 1024 * 1024; // 2MB のサイズ制限

export interface FileItem {
  name: string;
  path: string;
  size: number;
  modifiedTime: number;
}

/**
 * テキスト形式のファイルをスキャンしてフィルタリング
 */
export async function listTextFiles(): Promise<FileItem[]> {
  const dir = getBaseDir();
  const fileNames = await FileSystem.readDirectoryAsync(dir);
  const items: FileItem[] = [];

  for (const name of fileNames) {
    const ext = name.substring(name.lastIndexOf('.')).toLowerCase();
    if (SUPPORTED_EXTENSIONS.includes(ext)) {
      const info = await FileSystem.getInfoAsync(dir + name);
      if (info.exists && !info.isDirectory) {
        items.push({
          name,
          path: dir + name,
          size: info.size,
          modifiedTime: info.modificationTime * 1000
        });
      }
    }
  }
  return items.sort((a, b) => b.modifiedTime - a.modifiedTime);
}
```

## 3. 両プラットフォーム特有のインタラクションの差異処理

画面デザインを共有するという前提の下で、それぞれのネイティブプラットフォーム上でアプリを十分に洗練されたものに見せるために、プラットフォーム判定（`Platform.OS`）を通じて特有の操作動作を導入します。

### 3.1 保存されていない終了の傍受
エディターページに保存されていない変更があり、「戻る」をクリックした際、両プラットフォームはそれぞれのネイティブ傍受ロジックをアクティブにします：
*   **iOS のスワイプ戻るとナビゲーション戻る**：感知できない終了による変更の消失を防ぐため、デフォルトで iOS ネイティブのサイドスワイプジェスチャーを無効にします。戻るをクリックすると、画面下部から Action Sheet がスライドして表示され、破棄の二次確認を行います。
*   **Android 物理戻るボタンの傍受**：`BackHandler` を通じて物理的な戻るイベントと仮想ジェスチャーをハード傍受し、画面の中央に Elevation シャドウを伴う Material の中央配置の確認 Dialog をポップアップさせます。

```typescript
import { useEffect } from 'react';
import { BackHandler, Platform, Alert } from 'react-native';

export function useBackInterception(hasChanges: boolean, onBackConfirm: () => void) {
  useEffect(() => {
    if (Platform.OS !== 'android') return;

    const handleAndroidBack = () => {
      if (hasChanges) {
        showAndroidConfirmDialog({
          title: '保存されていない変更を破棄しますか？',
          onConfirm: onBackConfirm
        });
        return true; // 物理的な戻るを傍受
      }
      return false;
    };

    BackHandler.addEventListener('hardwareBackPress', handleAndroidBack);
    return () => BackHandler.removeEventListener('hardwareBackPress', handleAndroidBack);
  }, [hasChanges]);
}
```

### 3.2 仮想キーボードの競合問題と修正スキーム

#### 背景：自作のシミュレーションキーボード vs システム仮想キーボードの二重ポップアップの競合

`editor.html` には、WebView 内で Markdown のショートカット記号を備えた拡張入力体験を提供するための、完全な自作のシミュレーションキーボード（`.virtual-keyboard`、高さ 290px）が含まれています。しかし、以下の設計上の欠陥により、自作のシミュレーションキーボードとシステム仮想キーボードが同時にポップアップし、編集領域が二重に圧縮され、実際の編集可能なスペースがほぼゼロになるという事態が発生しました：

**競合の根本原因（元の誤ったロジック）**：
1. `DOMContentLoaded` イベントで `toggleVirtualKeyboard(true)` を呼び出し、シミュレーションキーボードを自動的に展開した（817〜820 行目）。
2. その直後に `document.getElementById('textarea').focus()` を呼び出して `<textarea>` にフォーカスを当て、システム仮想キーボードのポップアップをトリガーした。
3. 2 つのキーボードが同時に画面下部のスペースを占有した：システムキーボード（約 250〜340px）+ 自作シミュレーションキーボード（290px）。合計の圧縮高さは 580〜630px に達し、ほとんどのスマートフォンの画面の高さの 70% を超え、編集領域が完全に利用不可能になった。

**修正スキーム**：

「排他モード」を採用する——自作のシミュレーションキーボードとシステムキーボードのどちらか一方を選択し、決して同時にアクティブにしない：

- **システムキーボードのポップアップを完全に禁止する**：`<textarea>` に `inputmode="none"` 属性を追加する。この属性はブラウザ/WebView に対してこの入力ボックスがシステム入力メソッドを必要としないことを通知し、`<textarea>` のカーソルと選択範囲の能力を維持しながら、システムキーボードのポップアップを根本的に阻止する。
- **自動展開ロジックを削除する**：`DOMContentLoaded` で `toggleVirtualKeyboard(true)` を自動的に呼び出すコードを削除し、ユーザーがツールバーの「K」ボタンまたはフローティングキーボードアイコンを自発的にクリックした場合にのみシミュレーションキーボードを展開するように変更する。
- **シミュレーションキーボードが完全に入力を引き継ぐ**：すべてのテキスト入力、バックスペース、および改行は、システムキーボードを介在させることなく、シミュレーションキーボードの `typeKey()` / `typeBackspace()` / `handleEnterKey()` 関数を通じて `<textarea>` の値に書き込まれる。
- **`<textarea>` は focus を維持して利用可能**：`inputmode="none"` はカーソルの位置決めと選択範囲に影響を与えず、シミュレーションキーボードのすべての操作は依然として `textarea.selectionStart` / `setSelectionRange()` を通じて挿入ポイントを正確に見つける。

**両プラットフォームのキーボード回避パラメータ**（元のロジックを維持し、現在はシミュレーションキーボード自体の高さに対してのみレイアウトを行う）：
- **iOS**：シミュレーションキーボードが展開されたとき（290px）、`editor-container` は flexbox を通じて自動的に縮小し、それに伴い `textarea` の可視高さが減少するため、追加の `keyboardVerticalOffset` は不要（システムキーボードは完全に禁止されているため）。
- **Android**：`windowSoftInputMode` は `adjustResize` を維持するが、システムキーボードがポップアップしなくなるため、この設定はもはや実際の効果を生まない。将来の機能拡張のために保持する。


### 3.3 視覚コンポーネント特有のメカニズム
*   **プレス効果**：
    *   Android のカードはデフォルトで波紋の拡散効果 (`android_ripple`) を持つ。
    *   iOS は統一して `opacity` のグラデーションプレスフィードバックを提示する（Active 状態での不透明度を 0.6 に調整）。
*   **操作パネル**：
    *   Android のリストカードを長押しすると、画面の中央に Material 3 スタイルの角丸 Dialog メニューがアクティブになる。
    *   iOS のカードを長押しすると、画面下部からすりガラスのレイヤーの Action Sheet がスライドして表示される。

## 4. 画面の向きへの適応マトリックス

さまざまなシナリオでの最適な読書および編集体験を保証するため、`MobileFileEditor` はページごとに差別化された画面の回転戦略とレイアウトスキームを策定し、比例スケーリングや強制的なストレッチを徹底的に排除しています。

| ページ名 | デフォルトの向き | 回転戦略 | 核となる理由 |
|---|---|---|---|
| **ファイルリストページ (Index)** | 縦画面 (Portrait) | **縦画面にロック (Portrait Only)** | 純粋なカードリストとファイル管理ロジック。縦画面にロックすることで、片手での操作時にわずかな揺れによって誤って回転がトリガーされ、使用効率が低下するのを防ぐことができる。 |
| **テキストエディターページ (Editor)** | 縦画面 (Portrait) | **双方向適応 (Adaptive)** | テキスト/コードの編集中、横画面は十分な1行の幅を提供できる。横画面では編集エリアと Markdown プレビューエリアの2列分割ビュー (Split View) をサポートし、執筆体験を大幅に向上させる。 |

### 4.1 テキストエディターページ (Editor) の縦横画面の適応の詳細

縦横画面における自作シミュレーションキーボードとインターフェースの再配置戦略は以下の通りです：

#### A. 縦画面版のレイアウト構造 (Portrait Layout)
```text
+------------------------------------------+
|  [< 戻る]     ファイル名.md        [保存]  | <-- 上部ナビゲーションバー (60px)
+------------------------------------------+
|                                          |
|  これは Markdown ファイルです。          |
|  入力ボックスでカーソルが点滅しています...| <-- テキスト編集エリア (Flex: 1)
|                                          |
|                                          |
+------------------------------------------+
| [ # ] [ * ] [ - ] [ > ] [ ` ] [ [ ] [ K ]| <-- ショートカット記号バー (45px)
+------------------------------------------+
| [ A ] [ B ] [ C ] [ D ] [ E ] [ F ] [ G ]|
| [ H ] [ I ] [ J ] [ K ] [ L ] [ M ] [ N ]| <-- 自作シミュレーションキーボード (290px)
| [  Space  ]   [ Enter ]     [ Back ]     |     (inputmode="none" でシステムキーボードを無効化)
+------------------------------------------+
```

#### B. 横画面版の分割ビューとサイドバーレイアウト (Landscape Layout)
横画面では、縦方向の高さが非常に貴重になります（通常 360px〜420px の間）。高さ 290px のシミュレーションキーボードを展開し続けると、編集領域はほぼ完全に侵食されます。そのため、横画面では**分割ビュー + シミュレーションキーボードの折りたたみ**設計を採用します：

```text
+---+--------------------+--------------------+
| < |                    |                    |
|   | これは Markdown    | これは Markdown    |
| # | ファイルです。      | ファイルです。      |
|   | 入力ボックスでカ   |                    |
| * | ーソルが点滅して   | 入力ボックスでカ   |
|   | います...          | ーソルが点滅して   |
| - |                    | います...          |
|   |                    |                    |
| K |                    |                    |
|   |                    |                    |
| S |                    |                    |
+---+--------------------+--------------------+
  ^            ^                   ^
サイドバー    編集エリア (50%)     リアルタイムプレビュー (50%)
(80px)
```

**横画面の再配置と適応ロジック**：
1. **大型キーボードを非表示にし、サイドショートカットバーを保持**：横画面では自作シミュレーションキーボード（290px 版）を強制的に折りたたみ、画面の左端に幅 `80px` の縦方向の操作バーのみをレンダリングします。含まれるもの：戻る（`<`）、保存（`S`）、キーボード状態の切り替え（`K`）、および高頻度のショートカット記号（`#`、`*`、`-`）。
2. **2列分割ビュー (Split Screen)**：縦画面での単一ページの編集モードは、横画面では左右の均等な分割ビューに変更されます。左側の 50% の幅は `<textarea>` 編集領域であり、右側の 50% の幅は Markdown HTML がリアルタイムでレンダリングされるプレビュー領域です。両方の列は、すりガラスの境界線で区切られています。
3. **セーフエリアの動的補正 (Safe Area Insets)**：
   - 横画面時にスマートフォンにノッチがある場合（例：iPhone 14 Pro を横向き）、左側のナビゲーションバーの左パディング（`padding-left`）には `env(safe-area-inset-left)`（約 47px）を加算し、戻るボタンとショートカット記号がノッチに隠れないようにする必要があります。
   - 右側のリアルタイムプレビュー領域の右パディング（`padding-right`）は、視覚的な対称性とジェスチャーの安全性を維持するために、自動的に `env(safe-area-inset-right)` に一致します。

## 5. プロジェクトのリリースとグレースケール戦略

`MobileFileEditor` アプリのビジネス特性（ローカルファイルの読み取り、大きなファイルによる OOM クラッシュの発生しやすさなど）に基づいて、以下の両プラットフォームのカスタマイズされたリリース戦略を策定します：

### 5.1 iOS 側のリリース戦略 (MobileFileEditor_iOS)
1.  **内部ベータ版配布 (TestFlight)**：
    *   第1フェーズ：プラットフォーム検証チーム（合計約 50 人）を対象としたクローズドテストのために TestFlight 内部テストトラックに提出し、サンドボックスファイルシステムの大きなファイルのエラー傍受ロジックの検証に重点を置きます。
    *   第2フェーズ：TestFlight 外部公開テストリンク（定員 1000 人）を開放し、さまざまなデバイスモデル（ダイナミックアイランド、ノッチ付きスクリーン、iPad などを含む）でのキーボードの押し上げと回避の体験に関するフィードバックを収集します。
2.  **App Store への提出と審査**：
    *   アプリには機密性の高いローカルファイルの読み書きが含まれるため、ビルドしてパッケージ化された `Info.plist` に権限の用途宣言を正確に記入する必要があります。
    *   初期状態のリストが空であることによる「機能のないアプリ」としての誤判定でのリジェクト（Apple の審査のレッドラインの傍受）を防ぐために、シミュレートされたサンドボックスファイルのテストスイートのセットと画面録画のデモを App Store 審査チームに提供します。
3.  **段階的リリース (Phased Release)**：
    *   App Store Connect を通じて 7 日間の段階的リリースを開始します：
        *   1日目 1% -> 2日目 2% -> 3日目 5% -> 4日目 10% -> 5日目 20% -> 6日目 50% -> 7日目 100%。
    *   このグレースケールフェーズでは、Firebase Crashlytics を使用して、メインスレッドでの制限を超えるテキストファイルの読み取りによって引き起こされる `iOSError` および OOM のハングアップ率をリアルタイムで監視します。致命的な例外が発生した場合は、すぐに「リリースを一時停止」をクリックし、24時間以内にホットフィックスパッケージを作成します。

### 4.2 Android 側のリリース戦略 (MobileFileEditor_Android)
1.  **内部ベータ版配布 (Firebase App Distribution)**：
    *   内部ベータ版の APK を生成し、プラットフォームに統合された Firebase App Distribution を通じてプラットフォームの Android 検証チームのメンバーに自動的に配布し、さまざまな Android の深くカスタマイズされたシステムでの BackHandler の物理的な戻るボタンのハード傍受の効果を重点的にテストします。
2.  **Google Play クローズドテスト (Closed Testing)**：
    *   Google Play Console にクローズドテストトラックを確立し、指定されたテスターのリストをインポートして、公開トラックに入る前に、少なくとも 20 の主流の Android デバイス（さまざまなシステムバージョンと画面のパンチホール仕様をカバー）での実行テストに合格することを確認します。
3.  **段階的な公開 (Staged Rollout)**：
    *   Google Play プロダクショントラックに入ってリリースする際、段階的な公開を開始します：
        *   初期の割合：アクティブユーザーの **10%**。
        *   観察期間：**3 日間**。バックグラウンドでの ANR (App Not Responding) 発生率の収集に重点を置きます（UI スレッドをブロックする大容量ファイルの IO 操作の同期実行による ANR 例外を防ぐため）。
        *   段階的なリリース：ANR とクラッシュ率が安全な指標（<0.1%）の範囲内であれば、リリースする割合を 20%、50%、および 100% と順番に増やしていきます。
