本ドキュメントでは、独自開発した `gestalt-prompt-workflow`（ゲシュタルト美学プロンプトワークフロー）を、Antigravity IDE が提供するネイティブグローバルスキル生態系（Firebase バックエンド、Chrome DevTools パフォーマンス診断、Modern Web 仕様検索など）と詳細に比較し、その核心的な優位性と V2.0 で達成されたアーキテクチャの進化を解説します。

---

## 一、核心的な強み (Strengths)

純粋なエンジニアリング・ツール志向の公式スキルと比較して、独自開発の Gestalt Skill は「LLM の表現力チューニングと視覚アーキテクチャ」という領域において圧倒的な優位性を発揮します。

### 1. 「美学とアーキテクチャの共鳴」における空白を埋める
公式スキルライブラリ（`firebase-basics` や `debug-optimize-lcp` など）は、アプリケーションが「動くか」「速いか」というエンジニアリングの下限（ベースライン）を保証します。一方、Gestalt Skill はプロダクトの上限（クオリティの天井）を引き上げる視覚エンジンであり、知覚心理学（`GII`）と物理的インタラクション（`TPF`）を定量的制約として導入することで、LLM に高度な審美基準を付与します。

### 2. 「発散・収束」ワークフローによる凡庸さの打破
多くの公式スキルが一方向の指示型（仕様検索 → コード記述）であるのに対し、Gestalt Skill は対話型の `divergent_convergent_workflow` と高密度なリファレンス資産（`18_dark_lattice` など）の注入を組み合わせることで、LLM の学習データの平均化によって生じる「無難で退屈なカード型 UI」を打破します。

### 3. 高度に抽象化されたトークン化設計（宣言的制約）
複雑なデザインシステムを `design_prompt_template.md` 内のトークン早見表へと抽象化することで、生成コードの高い直交凝集性（`OCC`）を実現しました。LLM が恣意的な Hex カラーやマジックナンバーを生成することを防ぎ、保守性を飛躍的に高めます。

## 二、初期バージョンの課題と V2.0 での完全解決

初期バージョン（V1）の Gestalt Skill に存在したエンジニアリング上の制限は、V2.0 アップグレードですべて解決されました。

### 1. 実行可能な検証メカニズムの欠如 → **[`gestalt_linter.sh` により解決]**
- **公式スキルの基準**：`chrome-devtools` はコード生成後に実ブラウザへ接続して LCP を計測し、`firebase-security-rules-auditor` はルールの安全性を決定論的に検証します。
- **V1 の課題**：事前のプロンプト制約のみに依存し、CSS 内の `#ffffff` 直書きや `width` アニメーションを事後検証できませんでした。
- **V2.0 の解決策**：厳格な `verify_design_workflow.md` と Bash ベースの静的リンターを導入しました。

### 2. 静的コンテキスト読み込みによるトークン肥大化 → **[`asset_retriever.sh` により解決]**
- **公式スキルの基準**：`modern-web-guidance` は CLI/MCP 検索モデルを採用し、必要な Markdown セクションのみをオンデマンドで取得します。
- **V1 の課題**：テンプレートやケース全文を読み込むことでトークンを大量消費し、注意力の希釈を招いていました。
- **V2.0 の解決策**：軽量な `awk`/`grep` スニペット抽出スクリプトを実装し、`Prompt Snippet` のみを Agent に渡す設計へ刷新しました。

### 3. 低レイヤーの自動化スキャフォールド機能の欠如 → **[`init_project.sh` により解決]**
- **公式スキルの基準**：`firebase-basics` はプロジェクト初期化コマンドを自動実行します。
- **V1 の課題**：ディレクトリ骨格の立ち上げに複数回の対話が必要でした。
- **V2.0 の解決策**：ワンコマンドで `tokens.css` と標準ディレクトリを生成するスキャフォールドワークフローを導入しました。
